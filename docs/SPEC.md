# Snapbug — specification draft

Draft. The decisions below are the source of truth. The code may lag behind: that lag is a task in `docs/PLAN.md`, not an open question. Anything absent from this description and from the decisions is out of scope.

Do not start tasks marked TBD: an implementer agent must not take them.

## Product

A site owner installs the JavaScript SDK. A visitor opens the widget (a button or a hotkey), describes a bug, and submits a report. The SDK attaches an annotated screenshot, the environment, recent console errors, failed network requests, and a replay of the last few seconds (rrweb). Developers see tickets in the dashboard and leave internal comments.

There are several organizations, and each organization has several projects. Registration creates one organization by default. A user can belong to several organizations. A member may not have access to every project in their organization.

There are exactly two roles: member and administrator. A site visitor is not a user of the system. MCP is not a role. A member connects a normal MCP client with their own user token, and the agent acts only inside that member's projects. MCP does not accept a project key. The site uses that key only to create a ticket.

Ticket files (screenshot and replay) are stored in Vercel Blob. The product name is Snapbug. The interface language is English or Russian, switched in settings.

## Scope

In scope: email-and-password auth with acceptance of terms, password reset, invitations (expiry, resend, revoke, copy link), onboarding, the widget and ingest, the widget theme, kanban and the ticket card, comments, projects (archive, delete, default assignee, store IP, collect visitor email, color, slug) and key rotation, a member's access to a subset of projects, several organizations, users, organization settings (name, one retention period, require 2FA, one invite email domain, GDPR mode, delete workspace), an activity log of every application-object change, analytics, global search, playground, MCP through a normal client and the user token (`list_tickets`, `get_ticket`, `get_screenshot`, `update_ticket`, `add_comment`), languages en and ru, error responses that return the real status, ticket files in Vercel Blob, and demo data with a screenshot and a replay. A Jira connection is in the product; the detailed behavior is TBD.

## Non-goals

No GitHub integration, no ticket deduplication, no automatic report on a JS error, no MP4, no SSO/OAuth, no mobile SDKs, and no billing. No new roles. MCP has no resources, prompts, OAuth, replay, or project key. A mobile dashboard is not required. The widget on a phone is required.

## Decisions

1. Several organizations, each with several projects. A user can belong to several. An organization switcher already exists in the code. Onboarding stays: it creates the organization and the first project. `sign-up` does not create an organization.
2. A member may have access only to some projects in the organization. This is intentional. The code already does this (`project_accesses`; an admin sees every project).
3. Ticket files are stored in Vercel Blob. Without `BLOB_READ_WRITE_TOKEN` the code does not write to Blob. That is task P-09, not an open question.
4. The project key is only for widget ingest. Rotating that key is one action: the administrator issues a new key, the previous key stops working immediately, and the new secret is shown once. The project is not left with a dead key and no replacement. A member cannot rotate the key. There is no separate revoke that leaves the project without a replacement. That is P-02.
5. MCP is a normal MCP client connection. The member authenticates with their user token (shown once, stored as a hash, revocable). Bearer on `/mcp`. The project key is rejected. Tools are only `list_tickets`, `get_ticket`, `get_screenshot`, `update_ticket`, and `add_comment`, and only inside projects that member can access. Someone else's ticket is not found. Replay is not returned. In the code, `POST /api/mcp` accepts a key and can only create a report. That is P-03 and P-04.
6. Comments on a ticket are in scope. There is no comment storage and no comment screen. That is P-04.
7. Interface languages: English and Russian only. The user switches the language in settings. There is no switch. That is P-16.
8. The product name is Snapbug.
9. Password reset, analytics, and the widget theme stay in the product.
10. The ticket list is a kanban with columns New, In progress, Fixed, and Closed. There is no ticket table. Fixed stays Fixed.
11. Playground stays in the product as a demonstration. It is a sample customer page with the real widget. Submit does not call ingest and writes nothing to the database or to Blob. The page itself shows the captured screenshot, replay, environment, and logs. That is P-17.
12. Retention is one organization-level setting (`reports_retention_days`). There is no project-level retention. Deleting reports older than that period, including the screenshot and the replay, is not in the current implementation scope. Task P-08 remains and is marked TBD. An implementer must not start it.
13. A Jira connection is in the product. The detailed behavior is not specified. That is P-18, TBD. An implementer must not start it.
14. Global search runs in the current organization over tickets and the other main objects a member can open (projects), and respects project access. That is P-19.
15. Registration requires acceptance of the terms and stores that acceptance. That is P-20.
16. Project actions for an administrator: archive and restore, delete, default assignee, store visitor IP (default off), collect visitor email (default on; when off, the widget does not collect it), color, and a slug unique in the organization. That is P-21. GDPR mode (decision 18) overrides IP storage and email collection.
17. Invitation lifecycle: expire after 7 days, resend, revoke, and copy the current link. The invitee is a member. That is P-22.
18. Organization controls, administrator only: require 2FA (time-based one-time password), restrict invitations to one email domain, GDPR mode, and delete workspace. GDPR mode stops visitor IP storage and visitor email collection for every project. Delete workspace removes the organization and its data and does not delete user accounts. That is P-23.
19. The activity log records every change of an application object (tickets, comments, projects, keys, memberships, invitations, and organization settings): who, when, which object, and what changed. Not only keys, roles, and organization settings. That is P-07.
20. Error responses surface the real status the application throws (400, 401, 403, 404, 500, and any other real code). One static 500 page is not the only error. That is P-24.
21. Ticket comments sit at the bottom of the card. The thread shows the author, the time, and the text. The author can edit and delete their own comment. That is P-25.
22. An MCP user token has a name chosen at creation. The list shows the name, when it was created, and revoke. The secret is shown once and stored as a hash. That is P-26. `docker compose` starts Postgres only, not the app.
23. The activity page table is brought in line with the current dashboard and `@workspace/design-system`. The reference is those existing screens, not a new visual language. What the log records does not change. That is P-27.
24. The settings screen is brought in line with the current dashboard and `@workspace/design-system`. The reference is those existing screens, not a new visual language. Which settings exist does not change. That is P-28.

## Description and code

The description and the decisions are the intent. The code is what is already built.

1. **Repository.** One app, `apps/web`. Packages `server`, `validation`, `database`, `sdk`, `design-system`, `analytics`. `docker-compose.yaml` starts only Postgres. The README does not mention server, database, or sdk.
2. **Type contract.** Schemas and types live in `@workspace/validation`.
3. **Joining an organization.** The description says invitation only. The `membership.createMembership` procedure creates an administrator in the organization passed in, from a session (`create-membership.test.ts`). `identity.findUserCredentialsByEmail` returns `passwordHash` from a session.
4. **Invitation.** The invitation has no role, and the token is stored as plain text. Any member of the organization can send an invitation, not only an administrator (`send-invitation.use-case.ts`). An invitation expires after 7 days, and an expired one is not accepted. There is no resend, revoke, or copy link. That is P-02, P-12, and P-22.
5. **Keys, domains, masking.** Domains and privacy live in `projects.widget_settings`. A key is created on first read. `revoked_at` exists and a revoked key is rejected, but rotation is not one action that issues a replacement and shows the new secret once. Any member with access to the project can change widget settings (`project.router.ts`, without `adminMiddleware`). That is P-02.
6. **Ingest.** `POST /api/bug-reports`. Rate limiting exists for password reset, not for the project key. User-Agent parsing exists (`widget-user-agent.service.ts`). Visitor IP is not stored.
7. **Ticket.** The model has `short_id`, `board_order`, and `resolved_at`. Replay is a single `replay_key`. Statuses match the kanban: New, In progress, Fixed, Closed. Severity from the widget is low / high / critical, with no medium. Reproduction steps exist on the model; the SDK form does not collect them. The list is a kanban; filters run in the browser on the list that is already loaded.
8. **Audit.** The `audit_logs` table is tied to a project, not to an organization. It is written for some changes (project, key, ticket, project access). It does not record every application-object change. Role changes and organization settings are not audited. There is no log screen. Metadata has no `web | mcp` source. That is P-07.
9. **Retention.** `reports_retention_days` is one column on the organization. There is no project-level retention and no deletion by age. Deletion is not in the current implementation scope — P-08, TBD. An implementer must not start it.
10. **SDK.** `snapbug.identify` accepts `{ email }`. The screenshot uses `modern-screenshot`. The Alt+S hotkey exists. The email field is always shown. The email label promises the author a message when the bug is fixed; that mail does not exist — P-14.
11. **Already in the product.** Password reset, onboarding, analytics, the widget theme, and playground. The code has manual kanban order, `short_id`, and a playground screen. The screen currently initializes the real project key, so a submit creates a production ticket. Making it a local demonstration with no database write is P-17.
12. **Jira.** The connection is in the product. There is no detailed behavior — P-18, TBD. An implementer must not start it.
13. **Seed.** `packages/database/src/seed/bug-report.ts` writes screenshot and replay keys, not the files themselves.
14. **Indexes.** Migrations do not have the minimal `bug_reports (project_id, …)` indexes or a GIN index on logs.
15. **MCP.** `POST /api/mcp` authenticates a project key and exposes only create-report. There is no user token and no normal MCP client setup for the five tools. That is P-03 and P-04.
16. **Search.** There is no global search. That is P-19.
17. **Registration.** Sign-up does not store acceptance of the terms. That is P-20.
18. **Project actions.** Create sets the name and the color. Update changes the name only. There is no archive, restore, delete, slug, default assignee, store-IP setting, or collect-visitor-email setting. That is P-21.
19. **Organization controls.** Settings are the name and the retention period. There is no require-2FA, invite domain, GDPR mode, or delete workspace. That is P-23.
20. **Errors.** The error screen always shows 500 (`apps/web/src/client/modules/error/consts/texts.const.ts`). That is P-24.
