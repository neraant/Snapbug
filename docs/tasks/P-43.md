# P-43 MCP token scopes

Files: `packages/server/src/modules/user-token`, `packages/database/src/schema/user-token.const.ts` (+ migration), `apps/web/src/app/api/mcp/route.ts`, `packages/server/src/shared/orpc/mcp/*`, web `client/modules/user-token/components/create-user-token-dialog.tsx`.

## Goal

A token carries a set of scopes. A tool call is allowed only if the token has the tool's scope **and** the owner has the right (scopes can only narrow the owner's rights, never widen them).

## Scope model

Coarse, readable scopes (resource:action), derived from the P-41 catalog:

| Scope            | Allows                                                  |
| ---------------- | ------------------------------------------------------- |
| `tickets:read`   | list/get tickets, screenshot, logs, environment, search |
| `tickets:write`  | update ticket                                           |
| `comments:read`  | list comments                                           |
| `comments:write` | add comment                                             |
| `projects:read`  | list/get projects                                       |
| `members:read`   | list members                                            |
| `stats:read`     | overview stats                                          |
| `activity:read`  | activity (admin only)                                   |

`*:write` implies the matching `*:read`. Every tool in the catalog declares exactly one required scope. Optional: a token can also be limited to a subset of projects (picker of the owner's projects; default all).

## Behavior

- Created at token creation, immutable afterwards (to change, create a new token). Stored with the token; existing tokens migrate to the default of all scopes they have today (read + write on tickets and comments), so nothing breaks.
- `tools/list` for a token returns only tools whose scope it holds. Calling a tool outside scope returns an MCP error "This token does not have the `tickets:write` scope" and is audit-logged as a denied attempt only if cheap; no new audit requirements.
- Project restriction narrows what list/get tools return; others' tickets stay "not found".

## UI (creation dialog, step 1)

- Name field, then **Permissions** section:
  - Presets as a segmented control: **Read only** · **Read & comment** · **Full access** · **Custom**. Default Read only (least privilege).
  - Custom reveals grouped checkboxes (Tickets / Comments / Projects / Members / Stats / Activity), each row: label, plain description, and the tools it unlocks as muted monospace chips ("list_tickets, get_ticket…").
  - Write scopes show a small warning tone note "Allows the agent to change data".
  - Projects: "All my projects" radio or "Selected projects" with a multi-select.
  - Live summary line: "This token can use 9 of 14 tools".
- Token list shows scope chips (preset name or first 2 + "+N" with tooltip) and project restriction.
- The tool cards in P-42 show the scope chip; hovering the chip explains it.
- Uses `SecretRevealDialog` (P-31) afterwards.

## Tests

Use-case tests: scope allows/denies per tool, write implies read, owner's rights still apply, project restriction, migration default. One e2e: create a read-only token and see the write tools absent in the summary.

## Out of scope

OAuth, expiring tokens, per-tool granularity beyond the scope table.
