# P-55 E2E coverage of main flows beyond the happy path

E2E rules: `.agents/rules/common/e2e.mdc`. This task is an explicit request to cover main flows that are not only the happy path, so it overrides that rule’s “one happy path per file” and “no validation errors, empty states, or permission branches” limits for the specs listed below. Everything else in the rule stays: `getByRole` with a name plus visible text, no pixels, no `waitForTimeout`, no `data-testid` as the norm, naming `e2e/{context}/{verb}-{object}.spec.ts` with a singular context folder matching `apps/web/src/client/modules/`, seeds in `e2e/shared/seed/`. Do not add an e2e job to CI.

P-53 remains the place for the missing happy-path smokes (sign-up, onboarding, reset password, sign-out, ticket status and filters, open ticket, delete comment, project create/update/delete, team invitations, role and removal, token revoke, organization switch, and the rest of that brief). **Do not invent a second happy-path file for something P-53 already lists.** If P-53 has not landed a listed smoke yet, write it there (or in the file this brief names, once, and cross out the P-53 row). This brief adds unsuccessful paths, access control, the public SDK HTTP API, project-scope edge cases, and regressions for P-54.

Run the suite with `pnpm test:e2e` (see `.agents/rules/common/e2e.mdc`). The e2e server logs emails instead of sending them (`EMAIL_TRANSPORT=log`).

## Specs to add

### P1 — Auth

Extend or add specs so these paths are covered. Prefer extending `auth/sign-in.spec.ts` for successful sign-in and wrong password (two tests in one file are acceptable here, as in `shell/sidebar-order.spec.ts`). Do not replace P-53’s `auth/reset-password.spec.ts` or `auth/sign-out.spec.ts` if those are added there; if they are still missing, they may land in this task as the single happy-path file plus the extra cases below.

1. **Successful sign-in.** Submit a valid email and password, land on Overview (or the user’s landing page). This is the gap in today’s `auth/sign-in.spec.ts`.
2. **Wrong password.** Submit a valid email and a wrong password, stay on sign-in, see an error, do not get a session.
3. **Sign-out** (if not already landed in P-53): sign out from the user menu, land on sign-in, a protected URL redirects to sign-in. Also assert pending feedback once P-54 D-32 is fixed.
4. **Reset password via token** (happy path stays P-53). Here: a bad or expired token does not change the password; a used token cannot be reused. Issue the token through a seed helper; do not read real email or `.env*` files.
5. **Sign-up validation and limits** (regressions for P-54 D-01, D-02, D-17, and D-11 if the product hides enumeration): invalid email `notanemail` shows a format error, not “required”, and not two messages; a too-long name or email is rejected; empty required fields are rejected. Do not treat the P-53 / existing terms-and-register happy path as this work.
6. **Onboarding skip / exit paths.** A new user who can skip a step (invite teammates, or any existing Skip) still lands in a usable org/project state. A user who is already onboarded and visits `/onboarding` is redirected away. The complete-onboarding happy path stays P-53.

### P1 — Access control

These are the highest-value new tests. A member sidebar without admin links is not enough.

7. **Member denied on admin routes.** Sign in as a member and open administrator URLs directly (`/projects`, `/team`, `/activity`, Organization settings if that is admin-only). Expect a forbidden or not-found screen, or a redirect out of the admin UI — not the admin data. After P-24, prefer the real status page (`error/open-forbidden.spec.ts` in P-53) and reuse it.
8. **Member denied on admin oRPC procedures.** The same member calling administrator procedures (invite, rotate key, change a role, update organization, delete a project, and the like) gets a forbidden/unauthorized result and no data change. Use the app’s own client or a request helper with the member session; do not add `data-testid`.
9. **Cross-organization isolation.** A user (or a member session) in organization A cannot read or mutate organization B’s tickets, projects, comments, or settings by URL or procedure (IDs from a seed). Expect not-found or forbidden, never the foreign body.
10. **Read-only MCP token cannot write.** A token created with the Read only preset can call read tools and cannot call write tools (`update_ticket`, `add_comment`, or whatever the catalog marks write). Assert from the MCP HTTP entry, with the token in the header the product uses.
11. **Revoked credentials are rejected.** A revoked project API key cannot call `GET /api/widget-config` or `POST /api/bug-reports`. A revoked MCP user token cannot call tools. Rotation (already covered by `rotate-project-key`) should leave the previous key rejected; add the HTTP assertion here if that spec does not already do it.

### P2 — SDK public API

P-53 leaves the widget SDK package tests alone; this group is the **public HTTP API** the widget talks to, not a Playwright tour of the widget UI. Request-context tests are fine. Keep the `e2e/{context}/{verb}-{object}.spec.ts` naming (`report/…` or `sdk-setup/…`).

12. **Invalid or missing key.** `GET /api/widget-config` and `POST /api/bug-reports` with no key, a malformed key, or a wrong key are rejected. No ticket is created.
13. **Revoked key** — see item 11; may share a file with 12 if the setup is the same.
14. **CORS.** A request from an origin that is not in the project’s `allowedDomains` is rejected; an allowed origin can call the endpoints (preflight and/or the actual POST, matching what the widget does).
15. **Payload size limits.** An oversized body (or oversize screenshot/replay, within what the test can build quickly) is rejected with a client error, not a 500, and does not hang the suite. Stay inside a reasonable fixture size; do not raise global timeouts.
16. **Required fields.** `POST /api/bug-reports` without a title (and any other required field in the contract) is rejected. After P-54 D-18, a report that includes `stepsToReproduce` is stored and is visible on the ticket (this may be a UI assertion in `ticket-detail` or an API + UI follow-up).

### P2 — Tickets

17. **Status change** — happy path stays P-53 `ticket-board/change-ticket-status.spec.ts`. Here, if needed: an illegal transition is rejected, or a change is visible in the list and after reload. Do not duplicate the P-53 smoke.
18. **Kanban drag persists after reload.** Move a ticket to another column (prefer a keyboard or the status control if drag is flaky; if you use drag, make it stable). After a full reload the ticket is still in the target column and, after P-54 D-21/D-22, untouched tickets do not get a new “Last updated” only because of board-order normalization.
19. **Filters** — happy path stays P-53 `ticket-board/filter-ticket.spec.ts`. Here: a filter that matches nothing shows the empty state; clearing the filter restores the list; filters do not leak tickets from another project (with D-25).
20. **Project isolation on the board** (P-54 D-25). With a project selected (slug or UUID in the search param), the board shows only that project’s tickets, including after reload. No flash of another project’s tickets is required as a screenshot assertion — assert the tickets that must not appear are not in the DOM once the board is ready, and that a known foreign short id never appears.

### P2 — Project settings, slug / UUID, and P-54 regressions

21. **Project settings validation.** New project / settings: empty name is rejected; the default name is not a false “required” error (P-54 D-09). Other obvious client/server limits you already enforce should have one assertion each, not a matrix.
22. **Slug vs UUID project scope** (P-54 D-19). Open `/sdk` (and `/tickets` if cheap) with the project selected as a slug in the search param and as a UUID; both show the project’s SDK content / tickets after load. “All projects” on `/sdk` stays the empty state (unless a D-13 decision changes it).
23. **Regressions for fixed P-54 defects**, where a user-visible check is cheap and stable. Put them in the files above when they belong there; add a focused spec only when they do not. At least:

- D-01 / D-17: invalid email message (item 5).
- D-03: forgot-password gives the same visible result for a known and an unknown email (and still issues a token for the known one, via the seed/DB helper, not by reading mail).
- D-04 / D-30: no need to assert on the dev overlay; skip a brittle hydration test unless you have a stable console assertion. Prefer not to flake the suite.
- D-18: steps to reproduce are visible on the ticket (item 16).
- D-19 / D-25: items 22 and 20.
- D-20 / D-21: after a board move, `/activity` does not fill with “Normalize bug report board order” rows, and a normal update is readable.
- D-23: a long unbroken description does not need a pixel test; skip or assert the properties heading remains visible.

Do not add screenshot or pixel assertions for layout-only bugs (D-02, D-23, D-29).
