# P-34 Invitation flow rework

Current code: `packages/server/src/modules/invitation` (`accept-invitation.use-case.ts`, `find-invitation-by-token.use-case.ts`), web: `client/modules/auth/components/accept-signed-in-invitation.tsx`, `sign-up-form.tsx`, `sign-in-form.tsx`, `client/modules/team/components/invite-people-dialog.tsx`.

## Problem

The flow assumes the invitee has no account and goes through sign-up. A person who already has an account cannot reliably join: accept requires a matching signed-in session, there is no clear landing page, and every failure is a generic error. Treat this as a redesign, not a patch.

## Expected scenarios

The invitation email link opens a dedicated public page **`/invite/[token]`** (a full page in the `(auth)` layout, not a popup). The page first resolves the token and shows an invitation card:

> **{Inviter} invited you to join {Organization}** · role {Admin/Member} · "This invitation is for **a@b.com**" · expires in N days

Then, by case:

| Case                                     | What the user sees and what happens                                                                                                                                                                                                                   |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. No account with that email            | Primary: **Create account to join**. Email is prefilled and locked; name + password + terms (the existing sign-up fields). After sign-up the user is signed in, the invitation is accepted automatically, and they land in the organization overview. |
| B. Account exists, not signed in         | Primary: **Sign in to join**. Email prefilled and locked. After sign-in, the invitation is accepted automatically and the user lands in the organization overview. A "Forgot password?" link keeps the invitation token through reset.                |
| C. Signed in as the invited email        | Primary: **Join {Organization}**. One click accepts; no extra forms. Secondary: "Not you? Sign out".                                                                                                                                                  |
| D. Signed in as a different email        | Explain: "You're signed in as x@y.com, this invitation is for a@b.com." Primary: **Sign out and continue as a@b.com**. Secondary: "Go to app". Never silently accept for the wrong user.                                                              |
| E. Already a member of that organization | "You're already a member of {Organization}" with **Open {Organization}**. The invitation is marked consumed/harmless; no error screen.                                                                                                                |
| F. Expired                               | "This invitation has expired" + "Ask an administrator of {Organization} to send a new one" (show the inviter name). No form.                                                                                                                          |
| G. Revoked / invalid / already used      | "This invitation is no longer valid" + link to sign-in. Do not reveal whether the email has an account.                                                                                                                                               |

Success: a toast "You joined {Organization}", the joined organization becomes the active one, user lands on the overview. A user who belongs to other organizations keeps them; the switcher shows the new one.

## Inviting side (dialog and email)

- `Invite people` dialog: email input with chips (several addresses at once), role select, project-access picker (all projects by default, or a subset). Inline validation per chip. Inviting an email that is already a member shows "Already in your team" for that chip; inviting an email with a pending invitation offers "Resend" instead of creating a duplicate. Inviting someone who already has an account is allowed and works (case B/C).
- Result summary after submit: "2 invitations sent, 1 skipped (already a member)".
- Email template: shows inviter, organization, role, one **Accept invitation** button to `/invite/[token]`, expiry note. Text works for both new and existing users (no "create your account" wording).
- Tab Invitations (P-33): Resend / Revoke / Copy link keep working; Copy link copies the `/invite/[token]` URL.

## Logic requirements

- Accept is idempotent per user: second call for the same user/organization returns "already a member", not a 409 error page.
- Accept binds to the authenticated user and email match (case-insensitive); mismatch is a typed error that the page maps to case D.
- Invitation token lookup returns what the page needs (organization name, inviter name, role, invited email, status `pending|expired|revoked|accepted`, `accountExists` boolean, `alreadyMember` when signed in) without leaking more than that. `accountExists` is only returned for a valid pending token.
- Invitation role and project access are applied on accept (existing behavior).
- Keep the hashed token (P-12), 7-day expiry, resend replacing the old link (P-22).
- Add unit tests for each case A–G at the use-case level; add one e2e spec for the existing-user path (B) and one for the new-user path (A).

## Out of scope

SSO, domain restrictions (P-23).
