## 1. Validation and field limits (D-01, D-02, D-09, D-12, D-17)

### D-01, D-17. Invalid email is reported as “required”, and the browser also nags

- **Severity:** D-01 serious, D-17 cosmetic (same steps; fix together).
- **Problem:** On `/sign-up`, an email without `@` (for example `notanemail`) shows “Work Email is required” under the field, which is the wrong message. The browser also shows its native “Please include an ‘@’…” tooltip, so the user sees two messages at once. The same Zod pattern exists on sign-in and request-password-reset.
- **Steps:** Open `/sign-up`, type `notanemail` in Work Email, fill the other fields, submit.
- **Expected:** One message about format, for example “Enter a valid email”. Not “required”. Either the app or the browser speaks, not both.
- **Likely code:** `apps/web/src/client/modules/auth/schemas/sign-up.schema.ts` (line 7) uses `z.email(validationText.required(...))`. The same `z.email(validationText.required(...))` pattern is in `sign-in.schema.ts` and `request-password-reset.schema.ts`. If the input stays `type="email"`, disable native validation on the form (`noValidate`) or switch the input to `type="text"` and keep a single Zod message.
- **Acceptance:** `notanemail` on sign-up, sign-in, and forgot-password shows a format error only. An empty email can still say “required”.

- **Acceptance:** A name or email at the new max length is accepted and does not break those four places. A value over the max is rejected with a clear message. Existing long rows, if any, still wrap or truncate.

Decision: keep the current behavior for D-13, D-14, D-15, and D-28, and for D-11. See [ADR-007](../decisions/007-accepted-qa-gaps.md).

### D-13. SDK Setup is empty when “All projects” is selected

- **Severity:** minor, possibly by design.
- **Problem:** With “All projects” in the sidebar, `/sdk` only shows “Select a project in the sidebar to view install steps and the API key for that project.” Keys are per project, so this may be intentional, but the empty state is easy to miss.
- **Expected after a decision:** Keep the empty state but make the call to action clearer, or let the user pick a project on the page itself. Do not leave the page looking broken (that is D-19, which is not by design).
- **Tied to:** D-19 must still work when a project is selected.

### D-14. No dedicated API keys page

- **Severity:** minor, possibly by design.
- **Problem:** Settings has Profile, Preferences, Notifications, Organization. Project API keys live only on `/sdk` after a project is selected (Project API Key, Rotate key).
- **Expected after a decision:** Either this is accepted and `/sdk` is documented as the place for keys, or Settings (or a clear link from Settings) points there. P-49 already removed an Access tokens tab from Settings; do not bring a keys tab back without a decision.

### D-15. No in-app notifications for the actor’s own actions

- **Severity:** minor, possibly by design.
- **Problem:** An administrator who creates a project and works in the UI does not get notifications for those own actions. Incoming tickets created via ingest do appear.
- **Expected after a decision:** Either “do not notify the actor” is the rule and stays, or selected self-actions are notified. Write the rule so later notification work does not thrash.

### D-28. SDK snippet host is `https://your-app.com`

- **Severity:** minor, possibly by design (placeholder).
- **Problem:** The “Initialize the widget” snippet uses `host: 'https://your-app.com'`. Nearby copy talks about the API key and the ingestion host, so this looks like the Snapbug host, not the customer app origin.
- **Likely code:** `apps/web/src/client/modules/sdk-setup/utils/build-sdk-setup-snippet.util.ts` — `const host = input.hostExample ?? "https://your-app.com"`.
- **Expected after a decision:** Either keep a clearly labeled placeholder, or insert the real ingestion host (the current origin in local dev). The snippet comment/copy must match whatever `host` means in `@neraant/snapbug` `init({ apiKey, host, ... })`.
