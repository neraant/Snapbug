## Part B. Theme: one source of truth, no flicker

### Diagnosis (already done, confirm before fixing)

There are **three writers** of the theme and they fight:

1. `next-themes` (`ThemeProvider`) owns the `dark` class and `localStorage["theme"]`.
2. `UserPreferenceProvider` runs an effect that calls `setTheme(preference.theme)` and also manually toggles the `dark` class and rewrites two cookies on every preference change (`apply-user-preference-dom.util.ts`).
3. `buildUserPreferenceBootScript` adds/removes `dark` before hydration from the **cookie mirror**, while `next-themes` injects its own script reading **localStorage**. If they disagree, the page paints one theme, then flips.

The **sidebar** menu (`packages/design-system/.../layout/sidebar.tsx`) calls `setTheme` from `next-themes` directly. It changes `localStorage` and the class, but it does **not** save the preference to the server and does not update the cookie mirror. The next refetch of `findUserPreference` (or the effect in `UserPreferenceProvider` re-running) then re-applies the old server theme, which reverts or flips the theme. That is both "theme change in the sidebar does not work" and the flicker loop.

### Target design

- **`next-themes` is the only thing that touches the `dark` class and the first-paint script.** Remove the manual class toggling from `applyUserPreferenceDom` and the `theme` branch from `buildUserPreferenceBootScript` (the script and the cookie mirror may disappear entirely now that accent/density/motion are gone; delete `apps/web/src/shared/user-preference/*` and the `<head><script>` in `layout.tsx` if nothing else remains; keep `suppressHydrationWarning` on `<html>`).
- Server state `theme` is applied to `next-themes` **once**: on first load for a signed-in user whose server theme differs from `next-themes`' current value. Not on every refetch. Guard with a ref so the effect cannot loop. After the user changes the theme themselves, local choice wins until the mutation settles.
- **One hook** `useUserTheme()` in `apps/web/src/client/modules/preference/hooks/` returns `{ theme, setTheme }`: `setTheme` calls `next-themes` `setTheme` immediately (optimistic) and fires the `updateUserPreference` mutation. The Preferences tab and the sidebar both use it.
- The design-system sidebar must not import `next-themes` or know about the server. Give `SidebarLayout`/`SidebarUserMenu` props `theme` and `onThemeChange` (and keep `themeLabel`), passed from `app-sidebar.tsx` using `useUserTheme()`. Same for `auth-theme-toggle.tsx` on the auth pages (not signed in → `next-themes` only, no mutation).
- Disable transitions on theme switch (`disableTransitionOnChange` on `NextThemesProvider`) so there is no color animation flash.
- If the mutation fails, revert `next-themes` to the previous value and show the error toast.

### Acceptance for the bug

- Switch theme from the sidebar: it changes once and stays; reload keeps it; Settings > Preferences shows the same selection.
- Switch from Settings: sidebar menu shows the same selection.
- Network tab: exactly one `updateUserPreference` call per change, no repeated `findUserPreference` driven re-application.
- No visible flash on hard reload in both themes (dark user: page is dark from first paint).
- System theme follows the OS and updates live.

## Part B2. Language switch is broken: fix it

Symptom: choosing Русский/English in settings does not reliably switch the interface.

### Diagnosis

The hypothesis "the global replace `: () => void;` → `: VoidFunction;` broke it" is **not the cause**. That replace only touched type annotations, which are erased at compile time and cannot change runtime behavior (a `git diff` filter for non-annotation `VoidFunction` usages finds none, and the language files were not changed by it; `interface-language.ts` still has `new Set<() => void>()` and `subscribeInterfaceLanguage(listener: () => void)`). Do not revert it. Still, run `pnpm quality` after the fix to be sure types are fine.

The real, reproducible error is in the dev server log:

> Cannot update a component (`InterfaceLanguageProvider`) while rendering a different component (`InterfaceLanguageProvider`) ... at `setInterfaceLanguage` (`interface-language.ts:34`) at `InterfaceLanguageProvider` (`interface-language-provider.tsx:18`)

`InterfaceLanguageProvider` calls `setInterfaceLanguage(language)` **during render**. That function mutates the module-level `current` and calls every `useSyncExternalStore` listener synchronously, which schedules updates on other components while React is rendering. After the settings mutation, `router.refresh()` re-renders the `(app)/layout.tsx` with the new `language`, the provider (`key={language}`) remounts, and the store update during render races with the subscribers. Result: the switch is flaky or the texts stay in the old language until a hard reload.

Relevant files: `apps/web/src/client/modules/shared/locale/{interface-language.ts, interface-language-provider.tsx, use-interface-language.ts}`, `apps/web/src/app/(app)/layout.tsx` (AsyncLocalStorage `bindInterfaceLanguageStore` / `enterInterfaceLanguage` on the server), `apps/web/src/client/modules/user/hooks/use-interface-language-form.ts` (mutation then `router.refresh()`), `shared/queries/use-update-interface-language.ts`.

### Target

- No store mutation and no listener notification during render. The server-provided `language` must reach the client store **before** children render without notifying subscribers: initialize the module `current` synchronously only when it differs and **without calling listeners** during render (the first render of the tree already reads the right value through `getInterfaceLanguage`), and notify listeners from a `useEffect`/`useLayoutEffect` only if the value changed after mount. Pick one approach, keep it simple, and do not add a second store.
- `localize()` returns a Proxy that reads the active language at property access time. Components that read `texts.x` at module scope (not during render) never switch. Search for module-level reads of `texts.*` (constants built at import time, e.g. arrays of `{ label: texts.x }` defined at module scope) and make them lazy (getters like in `app-sidebar.const.ts`, or build inside the component). `app-sidebar.tsx` already depends on `language` in a `useMemo` for this reason.
- After a language change the whole visible UI switches within one navigation without a hard reload: sidebar, breadcrumbs, headers, dialogs, toasts, and `document.documentElement.lang`.
- Language persists after reload and sign-out/in (it is stored on the user, `identity.updateInterfaceLanguage`).
- The React warning above is gone from the browser console and the dev log.
- If the fix is purely client-side, no server or DB change is needed.
