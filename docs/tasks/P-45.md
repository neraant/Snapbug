# P-45 Notifications: backend and event model (part 1 of 3)

Parts: P-45 (this, data and events) → P-46 (bell, popover, inbox page) → P-47 (preferences and email). Follow the module layout rules (`.agents/rules/backend/overview.mdc`): new bounded context `modules/notification/` with `notification.contract.ts`, `notification.router.ts`, `application/{verb}.use-case.ts`, repository, port, entity, and a table `notificationTable` (`pgTable("notifications")`) in `packages/database` with a migration.

## Notification types (v1)

Chosen so that each one answers "do I need to act or know this?". Audience is stated so nobody gets noise.

| Type                                                | Audience                                                                                                             | Trigger                                            |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `ticket.assigned`                                   | the new assignee (not the actor)                                                                                     | assignee set on a ticket                           |
| `ticket.created`                                    | members with access to the project who are the default assignee, plus admins only if project has no default assignee | new report via widget                              |
| `ticket.status_changed`                             | the assignee and the reporter-less subscribers (see below), not the actor                                            | status changed                                     |
| `comment.created`                                   | assignee and everyone who commented before (thread participants), not the author                                     | new comment (web or MCP)                           |
| `mention`                                           | reserved, **not in v1**                                                                                              | —                                                  |
| `membership.role_changed`                           | the affected member                                                                                                  | role changed                                       |
| `project.access_granted` / `project.access_revoked` | the affected member                                                                                                  | project access changed                             |
| `invitation.accepted`                               | the inviter and admins                                                                                               | invitation accepted (new member joined)            |
| `project.archived`                                  | members with access                                                                                                  | project archived/restored                          |
| `security.api_key_rotated`                          | admins                                                                                                               | project key rotated                                |
| `security.token_created`                            | the token owner                                                                                                      | MCP token created (so a stolen session is noticed) |

Rules: never notify the actor about their own action. One notification per recipient per event. Respect project access at creation time and again when reading (a member who lost access no longer sees ticket notifications of that project).

## Data

`notification`: id, organizationId, recipientUserId, type, actorUserId (nullable; null for system/widget), objectType, objectId, projectId (nullable), `payload` jsonb (small display snapshot: ticket short id and title, project name, old/new value), `readAt` (nullable), `archivedAt` (nullable), createdAt. Indexes for (recipient, readAt, createdAt desc) and cursor reads.

Grouping key: `comment.created` and `ticket.status_changed` on the same ticket within 10 minutes collapse into one row with a counter (update `payload.count` and bump `createdAt`) rather than N rows.

## Producing events

A `NotificationService`/port called from the existing use cases in the same transaction as the change (tickets, comments, membership, invitation, project, key, token). It must not slow or fail the main action: failures are logged and swallowed. Use the existing audit hook points as the guide for where events happen.

## API (contract + router, not MCP)

- `notification.list` — cursor pagination, filter `unread | all`, type filter optional.
- `notification.unreadCount` — cheap count (used by the bell badge; polled).
- `notification.markRead` (ids), `notification.markAllRead`, `notification.archive` (ids).
- All scoped to the caller and active organization.

## Tests

Use-case tests: recipients rules per type (actor excluded, access respected, dedupe, grouping), list pagination, mark read, cross-user isolation (another user's notification is not found).

## Out of scope

UI (P-46), email and per-type preferences (P-47), realtime push (polling only in v1).
